# 本番への一括オペレーション

## 中心にある一つの事実

**あなたのスクリプトが持つ「今の状態」の認識は、本番システムの実際の状態とは別物である。**

一括処理の失敗はほぼ全てここから生まれる。スクリプトを止めてもサーバは動き続ける。投入直後の状態は投入前のまま。ログの「完了」はスクリプトがそう書いただけ。**判断の根拠は常にシステムに問い直す。**

この一点を握っていれば、以下の手順は自然に導ける。

---

## 最初に確かめること: その操作は繰り返してよいか

**以降の手順は「同じレコードに2回流しても結果が同じ」ことを前提にしている。** この前提が崩れると、中断・再開・やり直しのすべてが危険な操作に変わる。

着手前に、対象の操作について次を確認する:

| 問い | 崩れているときに起きること |
|---|---|
| 同じレコードに2回流して結果は同じか | 行が二重に作られる・金額が二重計上される |
| 外部 API を呼ぶか。課金や配信を伴うか | 再実行のたびに課金・通知が重複する |
| 通知・メール・Webhook を発火するか | 利用者に同じ連絡が複数届く |
| 中断された中途半端な状態から復帰できるか | 半端な状態が残り、次の実行が壊れる |
| 元に戻す手段はあるか（ロールフォワードのみか） | 誤りに気づいても戻せない |

**冪等でない操作を一括で流すなら、この手順書だけでは足りない。** 少なくとも次のどれかを備えてから着手する:

- **サーバ側の冪等キー** — 同じキーの再送をサーバが弾く。**これが最も確実**
- **副作用と同じトランザクションで書かれる完了記録** — 副作用と記録が原子的なので、片方だけ成立する状態が生まれない
- **再送前に「その副作用が起きたか」をシステムへ問い合わせて確かめる**（照合による再開）

**クライアント側の完了ログだけでは不十分。** 「副作用は成功したが、記録を書く前にプロセスが落ちた」という穴が必ず残る。再開時にその1件が済んだのか判らず、飛ばせば取りこぼし、流せば二重処理になる。**どちらを選んでも壊れる。**

そのうえで:

- **再開はやり直しではなく続きから**にする
- **不可逆な副作用（課金・通知・外部への書き込み）を最初に切り離す**か、テスト対象から外す

**冪等かどうか分からないなら、分からないまま流さない。**

**確かめ方は「本番で2回流してみる」ではない。** それ自体が、課金・通知・外部への書き込みを二重に起こしうる不可逆な実験になる。**確かめる行為が壊す**という構図を避ける。

順に当たる:

1. **設計と実装を読む** — 書き込みが upsert か insert か、外部呼び出しがどこにあるか、既存レコードを消してから作り直すのか追記するのか。**コードで判る**ことが多い
2. **手順書・スペックの記述**を探す。過去に同じ操作をした記録があれば、そこに副作用が書かれている
3. **副作用を切った非本番環境**（ローカル・ステージング・外部呼び出しをモックした構成）で2回流す
4. それでも判らないなら、**判らないという前提で設計する** — 処理済みを記録して飛ばす、不可逆な副作用を切り離す

**本番の1件で試してよいのは、上のいずれかで冪等性の確信を得たあと**である。そのときの1件は「冪等性の確認」ではなく「変更が意図どおり効くかの確認」であり、目的が違う。

---

## 着手前に決めること

### 1. 変更を貯めてから、一度だけ流す

一括処理は「修正 → 反映 → また修正 → また反映」に**分割してはいけない**。同じレコードを何度も回すことになり、時間も本番負荷も無駄になる。

**着手の条件**: 反映したい変更が全てデプロイ済みで、**当面それ以上変える予定がないこと**。

未確定の修正が残っているなら、**まだ流さない**。先に貯める。

### 2. 個別検証は本番でやらない

「1件で試したい」は、まず**手元の固定データ（fixture / スナップショット）で再現できないか**を考える。手元で再現できるなら本番を触る理由がない。

本番でしか検証できない場合だけ1件流し、**その1件は全件実行の対象から外す**（対象一覧から除く、または最後に流す）。

### 3. 実行中はコードを凍結する

流し始めたら、**処理対象の挙動に関わるコードは一切変更しない**。変更すれば、前半と後半で違う版が適用された不揃いな結果になる。

途中で修正が必要になったときの扱いは、**冪等かどうかで変わる**:

- **冪等なら**: 止めて、デプロイして、最初からやり直してよい。捨てるのは時間だけ
- **冪等でないなら**: やり直してはいけない。**止めた地点を記録し、残りだけを別の対象一覧で流す**。すでに処理したぶんは版が古いままになるので、その事実を記録して後で扱いを決める

だからこそ着手前に変更を貯めることが効く。やり直しの判断自体が発生しない。

## 対象集合を固定する

対象 ID を**ファイルへ書き出し、件数を数えて確認する**。実行中に対象が増減しても、このファイルが唯一の真実になる。

```bash
# 件数を必ず目視する。「65件のつもりが64件だった」は実際に起きる
wc -l targets.txt
```

**シェルで読むなら末尾改行を確認する。** `while read` は末尾に改行が無い最終行を静かに落とす。

```bash
tail -c1 targets.txt | od -c | grep -q '\\n' || echo >> targets.txt
```

**冪等な操作なら、完了したものを別ファイルへ追記しておくと再開が速くなる。** 対象一覧と完了一覧を分ければ、中断しても差分が残りだけになる。

**ただしこれは効率のための道具であって、正しさの担保ではない。** 「副作用は成功したが記録前に落ちた」1件は、このファイルからは判別できない。**冪等でない操作の再開は、サーバ側の冪等キー・原子的なチェックポイント・システムへの照合のいずれかで判断する**（冒頭の節を参照）。完了ファイルを根拠に飛ばしてはいけない。

## 事前スナップショットを取る

**後で「何が変わったか」を言えなくなるのが一番痛い。** 実行前に、比較したい値を保存する。

保存するもの:
- **集計値**（件数・合計金額など）だけでなく、**生成物そのもの**（成果物ファイル・レコードの主要フィールド）
- 上書きされるものは、実行後には二度と取れない

**一覧 API から集計するときはページングを必ず確認する。** 応答の `total` / `nextPageToken` と実際の件数を突き合わせる。`pageSize` を大きく指定したことは、全件返ってきた証明にならない。**ちょうど 200 / 100 / 50 のようなキリのよい件数が返ったら、まず打ち切りを疑う。**

**取れたことではなく、中身が入っていることを確認する。** スナップショットを1件だけ取り、**出力の全フィールドを目で見る**。`null` や空のフィールドが1つでもあれば、それは「元々値が無い」のではなく**取得コードがフィールドを取り違えている**可能性が高い。応答の実際のキー構造（`sorted(obj.keys())` など）を確かめてから直す。

**ここだけは事後にやり直せない。** 判定コードの誤りは気づいた時点で直せるが、**スナップショットの取りこぼしは、対象が上書きされた瞬間に永久に取り返せなくなる**。前後比較の柱が1本折れたまま「変化を説明する」段階に入ることになる。

## 投入前の確認

```
□ その操作が冪等か確認したか（冪等でないなら、続きから再開できる設計になっているか）
□ 反映したい変更が全てデプロイ済みか（稼働中のイメージタグ等で実体を確認。ワークフローの成功だけでは足りない）
□ 進行中のレコードが 0 件か
□ 対象一覧の件数が想定どおりか
□ 事前スナップショットを取ったか
□ 追加課金・外部 API 呼び出し・通知の有無を把握しているか
□ **完了判定のコードそのものを、実データで動かして確かめたか**
□ **ユーザーの承認を得たか**（下記。これが無ければ投入しない）
```

### 投入はユーザーの承認を得てから

**一括処理は不可逆である。** 既存レコードを消して作り直す・課金が発生する・利用者へ通知が飛ぶ、のいずれかに当たれば、実行後に「なかったこと」にはできない。CLAUDE.md も不可逆な操作にはユーザーの承認を求めている。

**上のチェックを全て通してから、実行の可否を尋ねる。** 準備が整っていない状態で尋ねると、承認そのものが意味を持たない。尋ねるときは次を添える:

- 対象の件数と、その集合をどう決めたか
- 事前スナップショットを取ってあること（何を保存したか）
- 冪等かどうか。冪等でないなら、中断時に何が起きるか
- 追加課金・外部 API 呼び出し・通知の有無
- 所要時間の見込みと、途中で止めた場合にどうなるか

**「準備ができたので流します」と宣言して実行しない。** 承認は事後報告ではない。

途中で対象や規模が変わったら**改めて承認を取る**。「65件の承認」は「別の65件」や「130件」の承認ではない。

**「進行中0件」は必ず投入直前に確認する。** 前の実行を止めた直後でも、サーバ側の処理は走り続けている。スクリプトを kill しても、投入済みの仕事は消えない。

### 完了判定のコードを、投入前に実データで動かす

**手順が正しくても、それを実装したコードが動くとは限らない。**

判定関数を1〜2件の実レコードに対して**単体で実行し、期待どおりの値が返ることを目で見る**。投入はしない。読み取りだけなので副作用が無く、数秒で済む。

```bash
# 例: 状態取得関数だけを2件で試す
for id in <既知のレコード2件>; do
  echo "$id → '$(state "$id")'"
done
# 期待: 'done<TAB>2026-...' のように status と時刻が返る
# 空・エラー・'?' が返るなら、投入前に直す
```

**確かめないと何が起きるか（実例）**: 状態取得関数に閉じ括弧の抜けがあり、常に空文字を返していた。すると「投入前から離れたか」も「終端に達したか」も永久に成立せず、**各レコードで待機ループの上限まで待つだけ**になる。1件20分・65件で11時間かかる計算だった。投入自体は成功しているので、**サーバ側は正常に見え、スクリプトだけが壊れている**。この形は気づきにくい。

**兆候**: 投入から十分な時間が経ってもログが1件も書かれない。**「まだ処理中なのだろう」と解釈せず、判定コードを疑う。** システム側の完了件数とログの件数が乖離していたら、ほぼ判定コードの問題である。

シェルスクリプトに他言語のコードを埋め込むときは特に危ない。**引用の入れ子は事故の元なので、判定ロジックは別ファイルへ切り出して構文チェックを通す**（Python は `python3 -m py_compile f.py`、シェルは `bash -n script.sh`）。

**投入の応答を捨てない。** 受理されたことを応答（実行 ID 等）で確認する。捨てると、拒否・タイムアウトで投入されなかったレコードに気づけず、**対象一覧には載っているのに処理されていない**という状態が静かに残る。

## 完了をどう判定するか

**ここが最も間違えやすい。**

投入した直後、レコードの状態は**まだ投入前のまま**である。「完了状態か」を見るだけだと、実際には何も始まっていないのに「完了」と判定してしまう。

**正しい判定は2段階**:

1. **状態が「投入前」から離れたことを確認する**（処理が始まった）
2. **その後、終端状態へ達したことを確認する**（処理が終わった）

判定に使えるものが状態名しかないなら、**更新時刻**も併せて見る。投入前の時刻のままなら、それは古い状態である。

**ログに書いた「完了」を信じない。** 進捗は最後にシステム側へ問い直して突き合わせる。ログとシステムが食い違ったら、システムが正しい。

**この判定を誤ると被害が連鎖する**: 「完了」と誤判定するとすぐ次を投入するため、意図した並列度を超えて一斉投入になり、キューが溢れて制御を失う。

---

## 並列度を決める

**サーバ側に同時実行の上限があることが多い。** クライアント側で並列度を上げても、キューが伸びるだけで速くならない。

**先に実測する**: 数件を投入して、同時に「処理中」になるレコード数を観察する。それがサーバの実効並列度。それ以上のクライアント並列は無意味どころか、キューを溢れさせて制御を失う。

手順書に「直列または低並列」のような指定があれば従う。**理由は外部 API のクォータやワーカースロットの保護**であって、速度のためではない。

---

## 実行中

- **定期的にシステム側の状態を集計する**（スクリプトのログではなく）
- **失敗を検知したら、その場で原因を1件見る**。同じ原因が全件に及ぶなら早く止めたほうがよい
- 長時間の実行では**認証トークンの期限**に注意する（レコードごとに取り直すのが安全）

---

## 完了後

```
□ 対象一覧の全件が終端状態に達したか（システム側で確認）
□ 失敗を原因別に分類したか。失敗のまま放置しない
□ 事前スナップショットと突き合わせ、変化を説明できるか
□ 想定外に大きく動いたレコードを個別に確認したか
```

**「変化した」だけでなく「なぜその変化か」を言えること。** 説明できない変化は、修正が効いた証拠ではなく、別の何かが起きた兆候かもしれない。

---

## 失敗の型と、それが教えること

実際に踏んだ失敗。**どれも「スクリプトの認識 ≠ システムの実際」という同じ根を持つ。**

| 起きたこと | 根 |
|---|---|
| 修正のたびに反映し、同じレコードを10件ぶん重複処理した | 変更を貯めなかった |
| 実行中にコードを変えて版がずれ、最初からやり直した | 実行中の凍結を守らなかった（やり直せたのは冪等な操作だったから。冪等でなければ二重処理になっていた） |
| 停止直後に再投入したら、前の処理がまだ走っていた | **止めたのはスクリプトで、サーバではない** |
| 65件のつもりが64件だった | 対象一覧の件数を数えなかった |
| 投入10秒後に古い状態を見て「完了」と誤記録し、全件を一斉投入した | **完了判定が「離れた」を見ていなかった** |
| 並列化したが速くならなかった | サーバ側の上限を実測しなかった |
| 一覧 API が200件で打ち切られ、集計を誤った | `total` と件数を突き合わせなかった |
| 完了判定の関数が構文エラーで常に空を返し、1件20分ブラインドに待っていた | **判定コードを実データで動かさずに投入した**（手順は正しく、実装が壊れていた） |

**最後の1つは特に重い**: その誤った集計を根拠に本番変更を進めていた。**本番を変える判断の根拠にする数値は、変更前に測り方そのものを検証する。**
