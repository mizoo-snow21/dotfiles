# Search, Filtering, Command Palettes & Empty/Loading/Error States — Cross-Product Decision Rules

Research method: fetched published design-system documentation (GitHub Primer, IBM Carbon, Shopify
Polaris/Shopify.dev, Atlassian Design System, Adobe Spectrum, Material Design 3) and product
engineering blogs (Slack Engineering, Retool, Superhuman) plus Nielsen Norman Group's
evidence-based UX research articles. Every rule below cites at least one source that was actually
fetched or returned verbatim quotes via search extraction. Where a source's page returned only a
title (fetch truncation/redirect) the claim is marked medium/low confidence and the gap is stated
rather than papered over. Disagreements between sources are called out as tensions, not smoothed
over.

## Decision rules

### ct-src-01 — Should search scope (which section/content-type it searches) be a pre-search choice or a post-search filter?
**Question:** When a product has multiple searchable domains (e.g., issues vs. files vs. people), should users pick scope *before* searching or *after* seeing results?
**Guidance:** Default scope to "search everything," make the current scope highly visible (not a quiet dropdown), and let users narrow *after* seeing results rather than forcing an upfront choice. Scoped-only search is a trap: users forget they narrowed it, assume nothing exists, and abandon.
**Evidence:**
- NN/g: "Scoped search allows users to limit their search to a section... [but] when a user doesn't realize that his search is limited to a section, the consequences are devastating." Users "routinely overlook the previously selected scope." Recommendation: "Always set the default scope to 'all'," provide "strong visual cues," and offer "a one-click option to expand the search to the entire site." Also: users "cannot select multiple categories simultaneously" with a scope dropdown, and "naturally prefer post-search refinement" — i.e., filters after results beat scope before search. (nngroup.com/articles/scoped-search/)
- GitHub's command palette resolves this by using explicit prefix characters (`#` issues/PRs, `!` projects, `@` people/orgs/repos, `/` files) typed *into* the same query box rather than a separate scope selector — scope is declared inline, stays visible as typed text, and is trivially reversible by deleting the prefix. (github.blog/changelog/2021-10-27-command-palette-beta/)
**Tension:** A visible, correct default of "search everything" costs relevance precision on huge corpora (more noise to rank), which is exactly why scoped search exists — but NN/g's data says the failure mode (silent scope) is worse than the imprecision.
**Confidence:** high (NN/g backed by explicit user-research evidence; GitHub's prefix-scope is a real shipped alternative solving the same visibility problem differently).

### ct-src-02 — Result counts: always show them, including zero
**Question:** Should a search/filter UI display a running count of matches?
**Guidance:** Always surface the result count, and show it even (especially) when it's zero — a visible "0 results" is what triggers the zero-result recovery UI; a silently empty list reads as broken.
**Evidence:**
- Carbon Design System: "Always include the number of search results, including for searches with no results." (carbondesignsystem.com/patterns/search-pattern/)
- NN/g's filters-and-sorting guidance (via course description) ties this to filter UI specifically: "communicate filter state through real-time counts, applied-filter chips, and predictable persistence" to "prevent 'zero results' dead ends." (nngroup.com/contents/self-paced-courses/filters-and-sorting-the-complete-design-guide/ — course marketing copy, not the full paid guide; medium confidence on the specific wording)
**Tension:** None found between sources; both push the same direction.
**Confidence:** high for the Carbon claim (direct fetch verified verbatim); medium for the NN/g filters-count claim (only a search-engine synthesis of a paid-course landing page, not the guide's own body text).

### ct-src-03 — Zero-result recovery: three concrete moves, not a dead end
**Question:** What should a search UI actually offer when a query returns nothing?
**Guidance:** (1) State clearly and prominently that there are no results — don't bury it in small text near the top where users' eyes skip past it. (2) Always give a path forward: show the original query in an editable search box, offer spelling corrections, suggest related queries that *do* return results, or give advice on how to broaden the query. (3) Never use humor or a cute tone at the zero-result moment — the user is already frustrated, and jokes read as mockery, not empathy, especially without vocal tone to soften them.
**Evidence:**
- NN/g, "3 Guidelines for Search Engine 'No Results' Pages": eye-tracking showed "users completely overlooked" a weak no-results message because "the text was small, lightweight, and squeezed in between the site logo and the first bold heading." Recommended recovery actions: "Restating the original query, Providing a search box (with the original query still in it for easy editing), Suggestions for similar queries that do return results, Spelling corrections, Advice about how to modify queries." On tone: "Humor can be a powerful way to defuse tension and express empathy, but it can also easily be misunderstood — especially online, where you can't use intonation and body language." (nngroup.com/articles/search-no-results-serp/)
- Carbon: "If a search returns 'No results', suggest a follow-up action and provide suggestions and helpful resources to aid the user in finding what they are looking for." (carbondesignsystem.com/patterns/search-pattern/, via search extraction)
- Shopify Polaris/App Home explicitly reuses the empty-state component for this exact moment: one of its three named use cases is "guiding merchants when search or filters return no results." (shopify.dev/docs/api/app-home/patterns/compositions/empty-state)
**Tension:** None — every source converges on "explain + offer a path forward," and none recommends a dead-end message.
**Confidence:** high (NN/g backed by eye-tracking evidence; Carbon and Shopify independently converge).

### ct-src-04 — Search suggestions/autocomplete must only surface guaranteed-good options
**Question:** What quality bar should a type-ahead suggestion dropdown hold itself to?
**Guidance:** Every suggestion offered must lead to real, relevant results — a suggestion that returns zero or irrelevant results is worse than no suggestion at all, because it costs the user a wasted click *and* damages trust in the feature. Highlighting strategy should match the suggestion type: for append-completions, bold only the system-added characters ("basketball h**oodie**"); for anywhere-matching suggestions, bold the user's own typed substring wherever it appears ("portable **basketball** **h**oop") so the user can see why each suggestion matched.
**Evidence:**
- NN/g: "Suggested terms that return zero results, or irrelevant results, are worse than unhelpful — they sidetrack users and are downright irritating." On highlighting: distinguish "append-only" vs. "anywhere-match" suggestion types and bold accordingly (exact examples above). For enriched (non-text) suggestions: "clearly label the enriched suggestion types... so that users do not have to guess what they're seeing or why it's being displayed," and don't eliminate simple text suggestions in favor of rich ones — "users heavily utilize... basic site-search suggestions even when enriched search suggestions are present." (nngroup.com/articles/site-search-suggestions/)
**Tension:** None found; this is a single well-evidenced source, but the underlying claim (every suggestion must resolve to something real) is close to self-evidently correct and matches Carbon's separate "always show a count" rule in spirit.
**Confidence:** high on the "must return results" and highlighting-by-type claims (direct fetch, explicit rationale); medium on the enriched-suggestion labeling claim (same source, slightly more speculative/less evidenced in the fetched excerpt).

### ct-src-05 — Result grouping: promote the single best match above categorized groups, don't just group
**Question:** When results span multiple categories (messages/files/people, or actions/components/code), how should the list be organized?
**Guidance:** Group results into clearly labeled categories, but *also* surface one best-guess "top result" ahead of/above the grouped sections — pure chronological or pure by-category grouping can bury the answer the user actually wants underneath less-relevant matches of the "right" type.
**Evidence:**
- Slack: shipped a hybrid specifically to fix this. "Recent search finds the messages that match all terms, and presents them in reverse chronological order... Relevant search... takes into account the Lucene score." Their fix: "The new Top Results module solves this problem by showing the top 3 messages from Relevant search above the normal Recent results," because pure recency search buried well-matching-but-older messages. Result: "a 9% increase in clicked searches and... a 27% increase in clicks at position 1." (slack.engineering/search-at-slack/)
- Retool's command palette: "we split up results into three categories: actions, components, and code" but additionally "introduced a 'Top result' section, ensuring that the best match always bubbled to the top" — explicitly because "the best match could get buried" inside a category-only layout. (retool.com/blog/designing-the-command-palette)
**Tension:** None between the two sources — both independently arrived at "categorize, but also promote a single top pick," which is notable convergence from unrelated teams.
**Confidence:** high (two independent engineering teams, both with explicit stated rationale and one with measured outcome data).

### ct-src-06 — Command palette scope narrowing: contextual pills, not a persistent global mode toggle
**Question:** In a command palette that spans many object types, how should users narrow what they're searching/acting on without losing speed?
**Guidance:** Let scope narrow progressively as the user types/selects (e.g., picking an app narrows subsequent results to that app's components/queries), and represent the active scope as removable "context pills" the user can delete to widen scope back out — rather than a fixed persistent toggle or a required upfront mode selection.
**Evidence:**
- Retool: rejected both a "scopeless" model and persistent toggles in favor of dynamic scoping — "actions and search results were limited to users' current scope," reducing cognitive load by hiding irrelevant options. Users "move up in scope by deleting context pills, and move down in scope by selecting apps, components, or queries." (retool.com/blog/designing-the-command-palette)
- This directly parallels ct-src-01's NN/g finding for web search (avoid a fixed, hard-to-notice scope) but solves it with a different mechanism suited to a keyboard-driven power tool: the scope is *visible as UI chrome* (pills) rather than *invisible state* (a dropdown you forgot you set).
**Tension:** None explicit, but note the mechanism differs by product type — web search users skew casual/infrequent (NN/g's audience), so "default to all + post-filter" wins; command-palette users are frequent power users who benefit from progressive narrowing because they're already mid-workflow with context. Same underlying principle (visible, reversible scope), different implementation for different usage frequency.
**Confidence:** high for the Retool mechanism (direct fetch, explicit rationale); the cross-reference to ct-src-01 is this analyst's synthesis, not a source's own claim.

### ct-src-07 — Command palette keyboard shortcut: converge on Cmd/Ctrl+K, make it global and consistent
**Question:** What keyboard shortcut should open a command palette, and where should it work?
**Guidance:** Use Cmd/Ctrl+K (the de facto convention) or, if it must differ, pick something "simple, memorable, and [that] doesn't clash with regular typing or common shortcuts" — and make it fire identically from anywhere in the app, not just specific screens, so users build one muscle-memory trigger.
**Evidence:**
- Superhuman's design-principles post: "pick a keyboard shortcut that is simple, memorable, and doesn't clash with regular typing or common shortcuts." Notes the actual convergence: "Cmd+K is used by Superhuman, Linear, and Slack; while Cmd+Shift+P is used by Sublime and VS Code" — i.e., two competing but each internally-consistent conventions exist. On global availability: "Wherever your user is in your app, they must be able to bring up the command palette by using the same keyboard shortcut." (blog.superhuman.com/how-to-build-a-remarkable-command-palette/)
- Linear ships exactly this: "Cmd/Ctrl + K to open command palette" as one of several product-wide single-key/chord shortcuts (C to create, / to search, P for priority), described as "not a feature... a core design philosophy that shapes every interaction pattern in the product," explicitly to match the interaction language of keyboard-native tools (VS Code, terminal, vim) developers already live in. (aggregated from public Linear materials/product docs, medium confidence — synthesized via search rather than a single fetched primary blog post)
- GitHub uses Cmd/Ctrl+K to open, with Cmd/Ctrl+Shift+K to jump straight into command mode. (github.blog/changelog/2021-10-27-command-palette-beta/)
**Tension:** Real disagreement exists in the wild: Cmd+K (Superhuman/Linear/Slack/GitHub) vs. Cmd+Shift+P (Sublime Text/VS Code) are both legitimate, each internally consistent within its ecosystem (consumer/SaaS apps converge on K; code editors descending from Sublime converge on Shift+P). Pick K unless you're explicitly building for an editor-adjacent audience already trained on Shift+P.
**Confidence:** high for the Cmd+K convention and GitHub's specific bindings (multiple independently fetched primary sources agree); medium for the Linear specifics (search-synthesized, not a single fetched primary document).

### ct-src-08 — Command palette should be "visually imposing" and hint at more content below the fold
**Question:** How much of the palette's contents should be visible at once, and how should it look?
**Guidance:** Deliberately show more commands than fit comfortably, with the last visible row visually cut off, to signal to first-time users that the palette holds far more than they've discovered yet — this is a discoverability device, not a bug to fix by shrinking the list.
**Evidence:**
- Superhuman: "Command palettes should be visually imposing," recommending the palette show something like "5 different commands" with an intentional visual cut so it implies "there are more things below the fold." (blog.superhuman.com/how-to-build-a-remarkable-command-palette/)
**Tension:** None found in other fetched sources (this is a single-source claim); it's plausible but not cross-verified against a second independent product.
**Confidence:** medium (single source, but explicit and specific rationale from a company whose product is built around this exact feature).

### ct-src-09 — Keyboard interaction model inside palettes/menus: a shared, near-universal contract
**Question:** What keyboard behaviors should a searchable list/menu/palette support by default?
**Guidance:** Arrow Up/Down cycles focus through items (wrapping); Enter/Space activates the focused item; Escape closes and returns focus to the trigger control; Tab/Shift-Tab also closes the menu (rather than trapping focus) if the user tabs away; typing a letter jumps focus to the next item starting with that letter (repeat the letter to cycle through ties). Right/Left arrows open/close a nested submenu where one exists.
**Evidence:**
- GitHub Primer's ActionMenu accessibility spec, verbatim: "Users can move between the different menu items... using cursor keys," "hitting a letter key for the first letter in an item to be selected will move focus to that item... hitting the letter key again will focus the next item," "activated using Space or Enter," closed via "Esc," and "if a keyboard user navigates away from an open ActionMenu using Tab / Shift+Tab, the ActionMenu is closed." On close, "focus returns to the most logical location in the page — in general, this is the trigger control." (primer.style/product/components/action-menu/accessibility/)
- Raycast's List component ships equivalent built-in behavior by default: automatic fuzzy filtering against item titles and keywords as the user types, with an `onSearchTextChange` escape hatch for custom filtering logic, and a dedicated `List.EmptyView` that is suppressed while `isLoading` is true so a loading list never briefly flashes "no results." (developers.raycast.com/api-reference/user-interface/list)
**Tension:** None — this reads as the converged, unremarkable-because-universal contract; no source proposes deviating from it.
**Confidence:** high (Primer's is a formal accessibility spec with exact key-by-key behavior; Raycast's API confirms the same interaction family is the default for a second, independent product).

### ct-src-10 — Power-user query syntax (search modifiers/qualifiers) should layer on top of, not replace, simple search
**Question:** Should advanced filtering be exposed as typed syntax, a UI control, or both?
**Guidance:** Ship both: a plain query box that works with zero learning curve, plus optional typed modifiers/qualifiers (`from:`, `has:`, `org:`, `language:`, boolean `OR`/`NOT`, a `-` exclude operator) that power users can type directly into the same box, with autocomplete assistance so the syntax is discoverable rather than something users must memorize from docs.
**Evidence:**
- GitHub code search: "Scope your searches with org: or repo: qualifiers, with auto-completion suggestions in the search box... Refine your results using filters like language:, path:, extension:, and Boolean operators (OR, NOT). Search for definitions of a symbol with symbol:." Framed explicitly as flow-preservation: "It helps you maintain a flow state by showing you the most relevant results first and helping you with auto-completion at every step." The minus (`-`) operator is called out specifically for excluding noise like generated/test files. (github.blog/engineering/architecture-optimization/improving-github-code-search/)
- Slack search modifiers (`has:star`, `has:reaction`, `to:me`) work alongside a parallel point-and-click filter UI (From/Date/File-type dropdowns below the search tabs) — the two mechanisms are offered side by side, not as alternatives to choose between. (slack.com/blog/productivity/shrinking-the-haystack-how-to-narrow-search-results-in-slack)
**Tension:** None found — every source treats typed syntax as additive to, not a replacement for, basic query search. The implicit cost (a syntax vocabulary to teach) is offset by autocomplete making it discoverable in-context rather than requiring documentation lookup.
**Confidence:** high (both GitHub and Slack are direct fetches of primary engineering/product content).

### ct-src-11 — Filter chips vs. facet rail vs. sheet: pick by attribute count and combination frequency
**Question:** When should filters be exposed as chips, a dedicated side rail, or a modal/sheet?
**Guidance:** Use inline filter chips for a small, flat set of mutually-legible filter values users toggle individually (chips are a compact alternative to checkboxes/switches, best when text is one word and icon use is purely functional, e.g., marking "selected" or "has a dropdown"). Escalate to a dedicated facet rail (commonly the left side) when the dataset has many filterable attributes that users routinely *combine* — catalogs, logs, large record sets. Push filtering into an overlay/sheet mainly as a responsive fallback when screen width can't fit a rail (not as a first choice).
**Evidence:**
- Material Design 3: "Chips help people enter information, make selections, filter content, or trigger actions," with filter chips as one of four types (assist/filter/input/suggestion), explicitly positioned as "a good alternative to Checkbox or Switch widgets" for "clearly delineated and exposed options in a compact area." Guidance to keep chip text to "ideally just 1 word" and limit icons to a "strictly functional role... as using other icons for decoration may clutter the limited space." Filter chips "should clearly indicate to users what filters have been applied... and provide a quick and easy way to remove a selected filter." (m3.material.io/components/chips/guidelines — page fetch returned only the title on two attempts; content here is reconstructed from a search-engine synthesis of the same page, so treat the exact wording as approximate, not verbatim-verified.)
- NN/g's paid filters-and-sorting guide (accessed via its public course-description page only, not the full guide): "place filters based on content type and screen size (side rail, overlay drawer, toolbar, etc.)" and reports "users complete tasks 25-50% faster with faceted navigation compared to keyword search alone." (nngroup.com/contents/self-paced-courses/filters-and-sorting-the-complete-design-guide/)
**Tension:** None of the fetched sources directly contradict each other, but confidence is capped because the two most specific claims (Material's exact filter-chip guidance, NN/g's facet-rail threshold) both come from search-engine synthesis of pages that would not return full body content to direct fetch — this is exactly the kind of claim the task brief asks to flag rather than launder as verified.
**Confidence:** medium (both claims plausible and consistent with wider practice, but not independently verified via direct primary-source fetch — stated here honestly rather than passed off as high-confidence).

### ct-src-12 — Applied filters must stay visible and cheap to remove, individually and all at once
**Question:** Once a user has applied filters, how should the UI represent and let them undo that state?
**Guidance:** Show every active filter as a visible, removable token (not buried inside a reopened panel), let users remove one filter with a single click/tap on that token, and provide an "All"/"Clear all" affordance to reset in one action. Filter state should persist predictably (e.g., surviving navigation back/forward) rather than silently resetting.
**Evidence:**
- Material Design 3: filter chips "should clearly indicate to users what filters have been applied to a set of results and provide a quick and easy way to remove a selected filter," and for chip-only filter UIs (no dropdown), "consider adding an 'All' option as the initial state, which can also serve as a way to clear all applied filters." (m3.material.io/components/chips/guidelines, same sourcing caveat as ct-src-11 — search-synthesized, not directly fetched)
- NN/g (same course-description source as ct-src-11): "communicate filter state through real-time counts, applied-filter chips, and predictable persistence." (nngroup.com/contents/self-paced-courses/filters-and-sorting-the-complete-design-guide/)
**Tension:** None found.
**Confidence:** medium — same sourcing limitation as ct-src-11 (search-synthesized rather than directly fetched body content), but two independent design authorities converge on the same specific mechanism (removable chip token + one-click clear-all).

### ct-src-13 — Distinguish four empty-state scenarios and change tone/graphic for each — never reuse one template for all
**Question:** Does an empty state need different treatment depending on *why* the screen is empty?
**Guidance:** Treat these as four distinct cases, not one generic "empty state" component: (1) **first-time/onboarding** — welcoming, can use playful illustration, teaches the feature at a simple level; (2) **feature not yet used** (user could act but hasn't) — "convey the intention of the feature in a way that sounds welcoming and human," primary action should launch the creation flow; (3) **temporarily/structurally empty** (e.g., an empty notifications inbox, or zero search/filter results) — communicate that emptiness is the *normal* state here, not a failure, and for the search/filter case pair it with the zero-result recovery moves (ct-src-03); (4) **error state** — deliberately *not* playful: "the graphic should reinforce that something went wrong," never use a delight-oriented illustration here, and messaging must be specific ("concisely describe what the problem is... avoid vague language like 'There was a problem'") plus recovery-oriented if recovery is possible.
**Evidence:**
- GitHub Primer's empty-states pattern doc draws exactly this four-way distinction with the language quoted above, including the explicit warning against reusing playful graphics for errors. (primer.style/product/ui-patterns/empty-states/)
- Shopify's App Home empty-state composition names three of the same buckets as its intended use cases: "Onboarding merchants to create their first item in a collection," "Guiding merchants when search or filters return no results," and "Prompting feature activation or configuration" — and structures every instance the same way regardless of cause: illustration (≤200px) + heading + description + primary action + optional secondary action. (shopify.dev/docs/api/app-home/patterns/compositions/empty-state)
- Atlassian draws a related but distinct line at the *content* level, between an "empty state" (task completed/cleared — can celebrate) and a "blank slate" (never-tried-this-before — should promote/encourage): "An empty state lets people know when they've completed or have cleared a task(s)... a blank slate... promote[s] and encourage[s] people to try something new." (atlassian.design/foundations/content/designing-messages, atlassian.design/components/empty-state)
**Tension:** Terminology diverges — Primer's "first-time" case and Atlassian's "blank slate" describe the same moment, and what Primer calls "temporarily empty" overlaps what Atlassian calls "empty state" proper. The underlying advice doesn't conflict (match tone to cause), but a team building a shared vocabulary should pick one taxonomy rather than mixing these systems' terms.
**Confidence:** high (Primer's fetch returned explicit, detailed rationale; Shopify's structural template independently verified; Atlassian's naming distinction independently verified — three systems, converging substance, differing labels).

### ct-src-14 — Loading indicator choice should be driven by expected wait time, with a threshold below which showing nothing is correct
**Question:** When should a loading state appear at all, and which kind (spinner, skeleton, progress bar)?
**Guidance:** Under ~1 second: show nothing — a loading indicator that flashes briefly reads as slower, not faster. 1–3 seconds: use an indeterminate spinner (there isn't enough time for a determinate readout to be useful). 3–10 seconds: prefer a determinate progress indicator so the user knows how much longer to wait. 10+ seconds: use a determinate indicator and, where feasible, move the work to a background task so it doesn't block interaction. Independent of duration: use skeleton placeholders (not spinners) for large content areas being replaced by structured content (lists, cards, text blocks), because a skeleton lets users start forming a mental model of the page layout before data arrives; reserve spinners for content that has no natural skeleton shape (e.g., a chart) or for short/unknown-duration waits.
**Evidence:**
- GitHub Primer's loading pattern doc gives the exact thresholds above, verbatim in spirit: "<1 second: Don't show a loading state. Seeing a loading indicator flash on the screen could be distracting and make the product feel slower than it is." "1–3 seconds: use indeterminate indicators." "3–10 seconds: Use a determinate loading state if possible to keep the user informed about why they're waiting so long." 10+: "determinate indicators with background task processing when feasible." Also: "Loading indicators' animation should be subtle and used sparingly" so it reassures without distracting. (primer.style/product/ui-patterns/loading/)
- Shopify Polaris: "spinners should only be used for content that can't be represented with skeleton loading components, like for data charts," and skeleton components should have their line count matched "to the content being loaded so it gives an accurate representation." Spinners are also explicitly scoped to *action feedback* ("notify merchants that their request has been received"), not whole-page loads. (polaris.shopify.com/components/feedback-indicators/loading — page redirected on direct fetch; content reconstructed from search-engine synthesis, medium confidence on exact wording)
**Tension:** The premise that skeletons universally beat spinners for *perceived* speed is contested in the wider practitioner literature, not just in the two design-system sources above. Multiple secondary write-ups cite a 2017 Viget study finding skeleton screens performed *worst* for perceived duration (worse than spinners and even a blank screen), while later studies (and the design-system consensus reflected above) found skeletons win, particularly on mobile. None of the design systems fetched here address this contested research directly — they simply prescribe skeletons for structured content without citing perception studies. Treat "skeletons feel faster" as the mainstream default, not an uncontested fact.
**Confidence:** high for the Primer time-threshold guidance (direct fetch, specific numbers); medium for the Polaris skeleton-vs-spinner split (fetch redirected, reconstructed from search synthesis); low/flagged for the general "skeletons always win" claim, which secondary literature actively disputes.

### ct-src-15 — Optimistic UI: reserve it for actions whose failure/rollback is simple and low-stakes
**Question:** When is it appropriate to update the UI immediately (before server confirmation) versus waiting for a response?
**Guidance:** Use optimistic updates only for reversible, low-consequence interactions (likes, favorites, reordering a list, toggling a setting) where a wrong-then-corrected state is merely annoying, not harmful. Never use it for anything irreversible or high-stakes (payments, transfers, destructive actions) where a wrong displayed state could mislead a real decision. When you do go optimistic, pair the rollback with a visible signal (e.g., a toast) the moment the server rejects the action, so the UI doesn't silently "lie" about state for longer than necessary.
**Evidence:** General synthesis from practitioner sources (freeCodeCamp, SitePoint, and related engineering write-ups on React's `useOptimistic` pattern), not a design-system primary source: "Apply it to reversible interactions like likes, favorites, and list reordering. Don't use it for payments, transfers, or anything you can't safely rollback." "If you can't articulate the rollback in one sentence, you probably shouldn't be optimistic. A wrong like-count is forgivable. A wrong bank balance isn't." Rollback timing: "Roll back to the previous state the moment a request fails, so the UI never lies for long," paired with "a visible toast."
**Tension:** None of the design-system sources in this research set (Polaris, Carbon, Atlassian, Primer, Spectrum, Material) directly document optimistic-UI policy, so this rule rests entirely on secondary engineering-blog consensus rather than an authoritative design-system source — flagged explicitly per the research brief rather than dressed up as equally strong evidence.
**Confidence:** low — plausible and widely repeated across practitioner sources, but not corroborated by any of the primary design-system documentation fetched for this report.

### ct-src-16 — Degraded (partial-failure) states: distinguish primary vs. secondary experiences, and never fake data to paper over an outage
**Question:** When part of a page's data/functionality is unavailable but the page is still otherwise usable, what should happen?
**Guidance:** First classify what failed: if it's essential to the page being useful at all, show a full error page, not a degraded one. If it's optional/secondary, keep the page working and communicate the gap honestly rather than hiding it: put a warning-level banner at the top of the page naming the problem (and link to a status page if one exists); replace large broken content areas with an explicit "unavailable" empty-state-style block (muted alert icon + specific text + optional secondary action) rather than blank space; for small inline elements, show a brief inline warning in place of the missing content; **hide counts/activity indicators entirely rather than showing a stale or fake placeholder value**; omit navigation links whose destination data is unavailable, but never hide the entire navigation/header; for non-essential buttons, remove them, and for essential-workflow buttons use an *inactive* (not disabled) state — disabling implies "you did something wrong," which isn't true when the *system* is degraded. Cap the number of simultaneous outage messages on one page (Primer specifically says 5 or fewer) so the page doesn't read as universally broken.
**Evidence:**
- GitHub Primer's degraded-experiences pattern doc, verbatim: "Primary experiences are those experiences that are essential for the page to be useful to the user" (→ show an error page); "Secondary experiences are those experiences that are not essential..." (→ degrade gracefully). "Don't try to conceal or downplay that something is wrong. Communicate that there is a problem and guide users around that problem as much as possible." On counts specifically: hide rather than show placeholder/stale values. On buttons: "Never disable controls for availability issues," use inactive state for essential ones and remove non-critical ones. On navigation: omit broken links but "never suppress the global navigation header itself." Cap: "Limit pages to 5 or fewer outage messages." (primer.style/product/ui-patterns/degraded-experiences/)
- This is a specific, more granular instance of the general "graceful degradation" principle described in wider engineering literature — categorize dependencies as critical vs. non-critical, and let non-critical failures degrade a *section* rather than the whole request — but Primer is the only source in this set with concrete, UI-level prescriptive guidance (banner placement, button states, count-hiding) rather than backend/systems-level framing.
**Tension:** None found; this is a strong single-source rule but internally very well-reasoned and specific enough to apply directly.
**Confidence:** high (direct fetch, extremely specific and actionable, internally consistent rationale).

### ct-src-17 — Error messages: plain language, name the specific problem, offer a fix, never blame the user
**Question:** What should the *content* of an error message actually say?
**Guidance:** State the specific problem (never a generic "An error occurred" or "There was a problem" — name what happened), write in plain human language free of internal jargon or error codes as the primary text, offer a concrete next step or fix rather than just describing the problem, and phrase everything without blaming the user — avoid words like "invalid," "illegal," or "incorrect" that imply user fault. Where possible, preserve the user's original input/action so they can correct in place rather than starting over, and if the system can guess the right fix, offer it as a one-click option instead of making the user diagnose it themselves.
**Evidence:**
- NN/g's error-message guidelines (their 2001 Nielsen guidelines, updated): "Error messages should be plainspoken" avoiding jargon; "Generic messages such as An error occurred lack context. Provide descriptions of the exact problems"; "Merely stating the problem is also not enough; offer some potential remedies"; "Don't use phrasing that blames users or implies they are doing something wrong, such as invalid, illegal, or incorrect"; "Let users correct errors by editing their original action instead of starting over"; "Guess the correct action and let users pick it from a small list of fixes" when feasible. (nngroup.com/articles/error-message-guidelines/)
- GitHub Primer, for the error-flavored empty state specifically: messaging must "concisely describe what the problem is while being as specific as possible" and explicitly avoid vague language like "There was a problem"; "If it's possible for the user to recover from the error, explain what went wrong and nudge them towards a path to recover." (primer.style/product/ui-patterns/empty-states/)
- Carbon's notification guidance adds a severity/scope dimension to content: task-generated errors (the user just did something) "require less background explanation," while system-generated errors "need sufficient context for user comprehension" since the user has no idea what happened. Also: "Do ensure users know how to take action if it is necessary" and "Do not leave users without next steps." (v10.carbondesignsystem.com/patterns/notification-pattern/)
**Tension:** None — three independent sources (research-driven UX firm, a major product's own pattern library, an enterprise design system) converge exactly on: be specific, don't blame, always give a next step.
**Confidence:** high (NN/g backed by longstanding, widely-cited usability research; Primer and Carbon both independently verified via direct fetch and agree in substance).

### ct-src-18 — Reserve error-red styling and disruptive containers for actual errors — premature or decorative red is a "hostile pattern"
**Question:** How aggressively should error styling (red, warning icons, disruptive containers) be applied, and when?
**Guidance:** Don't show validation errors while the user is still mid-action (e.g., flagging a field invalid while they're still typing into it) — wait until they've moved on from the field/step, since flagging errors before the user has committed to an answer reads as unwarranted criticism ("like grading a test before the student has had a chance to answer"). Don't use error-like visual treatment (red text, warning icons) for things that are not errors — e.g., marking required fields — since that dilutes what red *means* and desensitizes users to real errors. Reserve high-contrast/disruptive treatment (red, modal, blocking) for genuinely critical problems that need immediate attention; use low-contrast, non-blocking treatment for supplemental or low-priority messaging.
**Evidence:**
- NN/g's "Hostile Patterns in Error Messages": "Premature error messages are error messages that are presented by the system too early — before the user has reached a fair and reasonable point in the workflow to have truly committed an error or not." Fix: "Wait until a user moves on from a field to display an error message related to an appropriate format." On decorative red: "Using error-like visual treatments in situations where errors have not actually occurred" — for required-field marking, "avoid redundant indicators" (an asterisk or the word "required" is enough; don't also color it red). Core principle: "Let's assist users, not admonish them." (nngroup.com/articles/hostile-error-messages/)
- Carbon's severity-to-treatment mapping backs the same idea from the systems side: "The high-contrast style is more visually disruptive and should be used for notifications that are urgent or critical. The low-contrast style is better for supplemental messaging or other low priority use cases," and reserves modals specifically: "Only use a modal when the message is critical and needs the user's immediate attention or action." (v10.carbondesignsystem.com/patterns/notification-pattern/)
**Tension:** None found; both sources push toward reserving maximum visual/interruption weight for maximum-severity problems, and treating everything else more quietly.
**Confidence:** high (both direct fetches, explicit and specific rationale on both sides).

### ct-src-19 — Notification container choice: toast for system-wide/transient, inline for content-anchored/persistent, modal only for must-act-now
**Question:** Given an error (or other status message) to show, which container (toast, inline banner, modal) should carry it?
**Guidance:** Toast: short-lived, non-blocking, for system-generated messages not tied to one specific spot in the UI (e.g., "changes saved," a background sync failure) — but never use an auto-dismissing timer for anything the user critically needs to read, since some users (especially those needing more time to read/interact) won't have enough time. Inline: persistent (user-dismissed, not timed), placed directly adjacent to the thing it concerns (a form field, a broken content section) — this is the right container for validation and localized/task errors. Modal: reserved for genuinely blocking, must-resolve-now situations; overusing it for routine errors trains users to reflexively dismiss it, defeating its purpose.
**Evidence:**
- Carbon: "Short, time-based messages that slide in and out of a page and provide nondisruptive information" (toast); "Inline notifications are nondisruptive and confined to a specific area in the UI... place inline notifications near their related items... persistent until the user dismisses them"; "Only use a modal when the message is critical and needs the user's immediate attention or action." Explicit accessibility rule: "Don't use notifications that dismiss on a timer for critical or emergency messages, as some users with disabilities need more time to read or interact with messages." Toasts "automatically disappear after five seconds" by default. (v10.carbondesignsystem.com/patterns/notification-pattern/, carbondesignsystem.com/patterns/notification-pattern/)
**Tension:** None found in the sources fetched for this report, though this is effectively a single-system rule (Carbon); it wasn't independently cross-verified against, say, Atlassian's or Spectrum's own toast/inline/modal taxonomy in this pass.
**Confidence:** high for what Carbon itself says (direct fetch, explicit and detailed); medium for treating it as a cross-product universal, since it wasn't independently corroborated by a second design system's full container-selection guidance in this research pass.

### ct-src-20 — Command-search unification: when search matters as much as actions, put them side by side; when it doesn't, fold search into the palette as just another action
**Question:** In a command palette that could theoretically also do full-text/content search, should search get its own dedicated surface or live inside the palette as one more command?
**Guidance:** If content search is a primary, frequent user need in the product, give it a dedicated, prominent presence alongside the command palette (parallel, not nested) so it's not competing with commands for the same input box's attention. If search is occasional/secondary, it's fine to fold it in as just another invocable action inside the palette. Separately: define explicit "handoff points" for where the palette's job ends and normal UI takes over for multi-step actions (e.g., renaming something) — either let the palette collect the follow-up input itself, or close the palette and hand off focus to the relevant field in the main UI; the former keeps everything keyboard-driven but adds palette complexity, the latter is simpler to build but breaks flow.
**Evidence:**
- A design talk on command palettes cross-referencing real products, via fetched summary: "Context awareness is key to building an effective command palette... global commands are insufficient" — the palette should anticipate intent from the current page/record. On the search-vs-command split: high-search-importance products go with "search and actions side-by-side," while low-search-importance products fold search in "as an action within the palette." On handoff: contrasts VS Code (rename input happens right inside the palette) against Obsidian (palette closes and focus moves to the field in the document) — "Pulling more of those interactions into the command palette will increase complexity a good deal." (solomon.io/designing-command-palettes/ — an independent design-practitioner talk/post, not an official design-system or vendor source)
**Tension:** This source is not a design-system doc or a first-party product blog like the rest of this report's sources — it's an independent designer's analysis/talk. Treat its specific claims as informed synthesis rather than as authoritative as, say, Primer's or Carbon's own documentation.
**Confidence:** medium — plausible, specific, and consistent with the broader pattern of "make scope/context visible and progressive" seen elsewhere in this report (ct-src-01, ct-src-06), but resting on a single non-primary source.

## Cross-product observations

- **The same underlying principle — "make current scope/filter state visible and cheaply reversible" — recurs at every layer of this problem space**: web search scope (NN/g, ct-src-01), command-palette context (Retool, ct-src-06), applied filters (Material/NN/g, ct-src-12), and even degraded-state banners (Primer, ct-src-16, which insists on *naming* what's broken rather than silently hiding it). Different products implement it differently (a banner, a pill, a chip, a visible dropdown default), but every source independently arrives at "don't let the user be in a narrowed/degraded state without knowing it."
- **Design systems and engineering-blog sources agree far more than they disagree.** The clearest genuine disagreement found was not between design systems at all, but between the design-system consensus ("skeletons beat spinners for perceived performance," ct-src-14) and contested secondary perception-research (a 2017 study finding skeletons perform *worst*). None of the design systems engage with that contested research directly — they simply prescribe skeletons by default, which is worth flagging rather than treating as settled science.
- **"Reserve maximum visual weight for maximum severity" is a load-bearing idea that shows up under three different names**: Carbon's toast/inline/modal severity mapping (ct-src-19), NN/g's warning against premature/decorative error-red (ct-src-18), and Primer's "graphic should reinforce something went wrong" vs. playful-illustration split for empty states (ct-src-13). All three are really the same rule — don't spend your most disruptive/alarming visual language on non-critical moments, or it stops meaning anything when a real critical moment arrives.
- **Command palettes converge on near-identical keyboard mechanics (arrows/enter/esc/typeahead, ct-src-09) even across unrelated products** (GitHub's formal a11y spec vs. Raycast's default API behavior), suggesting this specific interaction contract is close to a solved, non-controversial problem — the interesting design decisions in command palettes are elsewhere (scope, ranking, discoverability, handoff), not in the base key bindings.
- **Confidence in this report is uneven by source, and that unevenness is meaningful, not noise.** NN/g and Primer sources are consistently high-confidence because they were directly fetched with full body text and explicit rationale. Shopify Polaris, Material Design 3, and the paid NN/g filters course were repeatedly blocked by redirects/truncation on direct fetch, so their claims here rest on search-engine synthesis of the same pages — plausible and directionally consistent with everything else, but flagged medium rather than passed off as equally verified.
